Course: AI/ML and Agentic AI Security
Module: 1, Applied Mathematics, Data Ingestion, and Feature Engineering
Status: design specification, v1. Synthetic data parameters below are design targets, not measured values.

---

## 0. Two problems to resolve before build

### 0.1 Timing conflict [Certain]

The syllabus gives Module 1 a single 35-minute lab. The three labs specified here contain twelve graded steps and roughly fifteen branching decision points. A learner who never takes a wrong branch needs about 90 minutes. A learner who takes wrong branches (which is the point) needs longer.

Options, in order of preference:

1. Lab 1 becomes mandatory self-paced pre-work with auto-grading. Lab 2 runs in the 35-minute in-class slot. Lab 3 is assigned as post-class homework, graded by the held-out file gate. This keeps the syllabus timing intact and puts the highest-value trap (leakage that looks like success) in front of the instructor.
2. Compress lectures 1.1 to 1.3 from 45 minutes to 30 and lecture 1.5 from 15 to 10, freeing 20 minutes. Run Labs 1 and 2 in class, Lab 3 as homework.
3. Run all three in class and accept that Module 1 becomes a 150-minute module. This breaks the 16-hour promise.

Option 1 is recommended. The rest of this document assumes it.

### 0.2 Runtime assumptions [Guessing]

I do not know what LabRunner executes. This design assumes the following. If any assumption is false, the failure-state mechanics change from live execution to canned screenshots, which is a materially weaker lab.

- Each step runs learner Python against a persistent kernel holding a shared state (a dict of DataFrames and fitted objects).
- LabRunner can run a hidden "probe" function after each step that inspects state and selects a feedback branch.
- LabRunner can hold a private dataset (the week-2 holdout) that the learner cannot read, only submit against.
- Decision points are rendered as choices, but the learner can also write free code; probes evaluate state, not which button was clicked.

The design uses three constructs throughout:

| Construct | Meaning |
| --- | --- |
| STATE | What exists in the kernel when the step begins |
| PROBE | Hidden check run after the learner submits |
| BRANCH | Feedback shown for each probe outcome |

## 1. Shared data environment: `acme-soc-w1`

One synthetic environment feeds all three labs. It is generated by a seeded script (to be built separately) so that every learner sees identical traps and the answer key is deterministic.

**Scenario frame.** Acme Industrial's SOC captured a six-hour window on a Tuesday (08:00 to 14:00 UTC). During that window a contracted red team operated from a single workstation on VLAN 40. The IR team reconstructed the timeline afterwards and applied labels from the ticketing system. A second week of data (`acme-soc-w2`) exists in which a different red team operated from VLAN 12 with different tooling. Learners never see w2 directly. It is the generalization gate for Labs 2 and 3.

**Sources.**

| Source | Format | Rows (target) | Deliberate defects |
| --- | --- | --- | --- |
| Zeek sensor-A conn.log | TSV with `#fields` header, `-` for unset, `(empty)` for empty sets, `ts` as epoch float | 180,000 | Log rotation replayed 02:00 to 02:15 segment: 4,100 exact duplicate rows |
| Zeek sensor-B conn.log | JSON Lines, `ts` as ISO 8601 with a local offset of +02:00 | 95,000 | Tapped on the same span as sensor-A for VLAN 40 only: 34,000 flows appear in both sensors with different `uid` values and clocks skewed by 0.3 to 0.8 seconds |
| Windows Security EVTX (40 hosts) | Raw `.evtx` read via python-evtx, XML per record | 62,000 events | 12% of 4624 events lack `LogonType` and `ElevatedToken` (older template version); 3 hosts write `SystemTime` in local time despite the UTC suffix; 1% of chunks are corrupt and raise on parse |
| Flow export (CICFlowMeter-style) | CSV | 140,000 | `Flow Bytes/s` and `Flow Packets/s` contain literal `Infinity` and `NaN` where `Flow Duration` is 0; column names carry leading spaces; the `Fwd Header Length` column appears twice; timestamps are 12-hour format with no AM/PM marker |
| Ticketing export | CSV | 1,900 | Provides `label`, `ticket_id`, `analyst_note`. Positives only. |

**Base rate.** Week 1: 1 positive flow per 180 (red team was active for a long time in a small network). Week 2: 1 positive per 2,000. The gap is deliberate: it makes the base-rate lecture concrete when learners compute PPV at the end of Lab 2.

**Beacon.** Host 10.40.7.22 connects to 198.51.100.14:443 every 60 seconds for the full window (360 flows, near-identical bytes). It is benign in the labels (an EDR heartbeat) and exists to punish over-aggressive deduplication.

## 2. Lab 1: Data Ingestion Under Chaos

### 2.1 Scenario

You are the detection engineer who inherited the Module 1 dataset request. Three collectors, one ticketing export, and a Slack message from the SOC lead: "Get me one clean table of flows with host logon context by end of day. The data science team keeps saying our data is unusable." You must produce a single typed pandas DataFrame from all four sources, with provenance, that Lab 2 can train on.

The security stake: every row you cannot trace to a source is a row an attacker could have inserted. The syllabus lists training-data poisoning via the ingestion pipeline as a Module 1 threat. This lab is where the control (row-level provenance) is built.

### 2.2 LabRunner flow

**Step 1: Load everything and watch it fail**

STATE: four file paths in `SRC`, empty `state` dict.

Learner action: choose a loading approach.

| Choice | System response |
| --- | --- |
| A. `pd.read_csv` on all four | Sensor-A: the `#fields` line becomes row 0 and every column is `object`. Sensor-B: `ParserError: Expected 1 fields in line 2, saw 19` (JSON Lines is not CSV). Flow CSV: loads, but `Flow Bytes/s` dtype is `object` because of `Infinity`. EVTX: `UnicodeDecodeError`. |
| B. Format-specific parsers (custom TSV reader honoring `#fields`, `pd.read_json(lines=True)`, python-evtx iterator, `pd.read_csv` with `na_values`) | Sensor-A and sensor-B load. Flow CSV loads with `Infinity` still present unless `na_values=['Infinity']` was passed. EVTX iterator raises `struct.error` at chunk 37. |
| C. Learner-written code | Probe inspects outcomes as above. |

PROBE: `state` contains four DataFrames; `zeek_a.ts` is float; `zeek_b` has 19 columns; EVTX parse did not abort.

BRANCH feedback (on EVTX abort): "One corrupt chunk killed your entire host-context feed. In production, a collector that stops on the first bad record is a collector an attacker can silence with one malformed event. Wrap the record iterator, log the failure with the chunk offset, continue."

BRANCH feedback (on `Infinity` still present as string): "Your rate columns are text. Nothing downstream will scale, split, or train on them. You will find out in Lab 3 when `StandardScaler` throws. Fix it here."

**Step 2: Fix the schema**

STATE: four raw DataFrames.

Learner action: map every source to a common flow schema (`ts_utc, src_ip, src_port, dst_ip, dst_port, proto, service, duration, orig_bytes, resp_bytes, orig_pkts, resp_pkts, conn_state, history, source_sensor, source_file, row_hash`).

Decision point: what to do with `Infinity` and `NaN` in the flow rate columns.

| Choice | Outcome | Feedback |
| --- | --- | --- |
| Drop the rows | Removes 6,200 rows. PROBE detects that 71% of dropped rows have `conn_state in (S0, REJ)` and `orig_pkts == 1`. | "You just deleted the SYN scan. Zero-duration single-packet flows are the shape of reconnaissance. The defect in the exporter's rate calculation is not a defect in the record." |
| Replace with 0 | Rate columns now conflate zero-duration flows with genuine zero-throughput flows. | "A one-packet flow with duration 0 has undefined rate, not zero rate. You have merged two different populations. Lab 2 will show this as a feature that looks noisy for no reason." |
| Replace with NaN and add `zero_duration` boolean flag | Correct. | "Undefined stays undefined. The flag preserves the signal. Imputation is a pipeline decision, not an ingestion decision, and you will make it inside the Pipeline in Lab 3." |

Second decision point: the duplicated `Fwd Header Length` column.

| Choice | Feedback |
| --- | --- |
| Keep both (pandas renames the second to `.1`) | "Two columns, identical values. Any tree model will split importance across them at random and your Lab 2 importance chart will lie to you." |
| Drop one after confirming equality | Correct. PROBE verifies the learner checked equality rather than assumed it. |

**Step 3: Normalize timestamps**

STATE: schema-aligned DataFrames, `ts` still in three formats.

Decision point: timezone handling.

| Choice | Outcome |
| --- | --- |
| Parse everything as naive and concatenate | Sensor-B rows land two hours away from their sensor-A twins. The beacon appears as two interleaved series. PROBE: fewer than 5% of the 34,000 cross-sensor pairs align within 2 seconds. |
| Assume all UTC | Same failure for sensor-B, plus the three misconfigured Windows hosts land in the wrong hour. |
| Per-source timezone, convert to UTC, tz-aware dtype | Correct for Zeek. PROBE then checks whether the learner detected the three Windows hosts. |

Trap within the trap: the flow CSV's 12-hour timestamps with no AM/PM. Two rows read `3:30`. The only way to resolve them is to use the fact that the exporter writes records in arrival order, so the file is monotonic in time. Learners who parse naively get a six-hour window that folds into three.

BRANCH feedback: "Your flow file covers 08:00 to 14:00 but your parsed range is 01:00 to 02:00 and 08:00 to 12:00. Where did the afternoon go? Look at the raw strings. This is a real defect in a widely used public dataset, and the fix is ordering, not parsing."

PROBE: all `ts_utc` columns are `datetime64[ns, UTC]`; cross-sensor pair alignment above 95%; flow file range spans six hours; the three misconfigured hosts are shifted (learner must have compared each host's logon times against Zeek's first-seen time for that host IP).

**Step 4: Deduplicate**

STATE: one concatenated flow table of about 419,000 rows (before dedup), 4,100 exact dupes, 34,000 cross-sensor dupes, 360 beacon rows.

Decision point: dedup key.

| Choice | Rows removed | Feedback |
| --- | --- | --- |
| `drop_duplicates()` on all columns | 4,100 | "You removed the replay. You did not remove the 34,000 cross-sensor twins because `uid`, `ts` and `source_sensor` differ. Exact-match dedup finds only the duplicates that were never going to fool anyone." |
| Drop on `uid` | 0 | "uid is generated per Zeek instance. Two sensors, two uids, one flow." |
| Drop on 5-tuple | about 38,000 plus the beacon collapses to 1 row | "You found the twins and then destroyed the beacon. A host that repeats the same connection every 60 seconds is one of the highest-value signals in this dataset, and your dedup rule just called it a duplicate." |
| Drop on 5-tuple plus `ts_utc` rounded to 1 second plus `orig_bytes` | 34,000 plus 4,100 | Correct. PROBE confirms beacon count is 355 to 365. |

Provenance requirement (graded): every surviving row carries `source_sensor`, `source_file`, and `row_hash` (SHA-256 of the raw line). When a cross-sensor duplicate is removed, the survivor's provenance lists both sensors.

BRANCH feedback on missing provenance: "You cannot answer 'which sensor produced this row' anymore. If sensor-B is compromised and starts feeding fabricated flows, you have no way to isolate them. The syllabus calls this the ingestion poisoning threat. The control is the column you just skipped."

### 2.3 Data design summary

| Trap | Where | Detection method the learner must find |
| --- | --- | --- |
| Exact replay duplicates | Sensor-A 02:00 to 02:15 | Any dedup |
| Cross-sensor hidden duplicates | 34,000 VLAN 40 flows in both sensors | Key on 5-tuple plus time bucket plus bytes, after timezone normalization |
| Beacon destroyed by over-dedup | 10.40.7.22 heartbeat | Count of surviving beacon rows |
| Infinity as text | Flow rate columns | dtype inspection |
| Rows dropped are attack-shaped | Zero-duration flows | Distribution of `conn_state` in dropped rows |
| 12-hour timestamps | Flow CSV | Parsed range sanity check |
| Three hosts on local time | EVTX | Cross-reference against Zeek first-seen |
| Corrupt EVTX chunk | Chunk 37 | Parser must not abort |

### 2.4 Failure modes

- Learner's final table has 385,000 rows (twins not removed). Lab 2 will show inflated performance because twin rows straddle any random split.
- Learner's final table has 347,000 rows and one beacon row. Lab 2 loses the beacon feature entirely.
- Timestamps are naive. Lab 3's time-ordered split silently interleaves sensor-B into the wrong period.
- EVTX join yields 40% null host context because misaligned hosts never match a Zeek window.

### 2.5 Instructor notes

- Emphasize: the defects here are not exaggerations. Infinity strings, doubled columns, and ambiguous 12-hour timestamps are all present in CIC-IDS2017 [Likely; verify against the specific CSV release you distribute]. Learners should leave knowing that "public benchmark" does not mean "clean".
- Common mistake: learners deduplicate first, then normalize timestamps. Order matters. The cross-sensor twins are only visible after timezone alignment.
- Teaching moment: the SYN scan deletion. Ask the room what fraction of their SOC's detections would survive a data engineer who "cleaned" zero-duration flows.
- The beacon is the bridge to Module 2 (sequence models) and Module 8 (anomaly thresholds on tool-call frequency). Say so.

### 2.6 Success criteria

- Final table: 380,000 to 382,000 rows. [Design target; exact value fixed by the generator seed.]
- Beacon rows: 355 to 365.
- All timestamps tz-aware UTC; flow file spans six hours.
- Provenance columns populated on 100% of rows.
- EVTX join rate above 90% of 4624 events matched to a Zeek host window.
- Learner has written one markdown cell explaining why zero-duration rows were kept.

## 3. Lab 2: Feature Engineering and Hidden Leakage

### 3.1 Scenario

Detection engineering wants a triage model that ranks flows by probability of red-team activity so analysts look at the top of the queue first. You have the Lab 1 table joined to the ticketing labels. A data scientist on the team already built a "quick baseline" that hit 99.8% accuracy and has a slide deck ready for the CISO. Your job is to find out whether the number is real before the deck ships.

### 3.2 Feature pool

| Type | Columns |
| --- | --- |
| Numeric | `duration, orig_bytes, resp_bytes, orig_pkts, resp_pkts, bytes_per_pkt, orig_ttl, host_alert_count_24h` |
| Categorical | `proto, service, conn_state, dst_port, source_sensor` |
| Text | `history` (Zeek flag string), `cmdline_window` (4688 command lines from the same host within 10 minutes of the flow, concatenated) |
| Label-adjacent | `ticket_id, analyst_note, label` |

### 3.3 The leakage inventory (answer key)

Ordered from obvious to subtle. RF importance rank is the design target for the learner's first model.

| # | Feature | Type of leak | RF importance rank | How it leaks | How to catch it |
| --- | --- | --- | --- | --- | --- |
| 1 | `analyst_note`, `ticket_id` | Label leakage | 1, 2 | Populated only for positives | Null rate by class |
| 2 | `orig_ttl` | Proxy leakage | 3 | Red-team workstation emits TTL 64; the Windows fleet emits 128. TTL identifies the source OS, not the behavior. Mirrors the `sttl` problem in UNSW-NB15 [Likely]. | Single-feature AUC near 1.0; value distribution by class is bimodal with no overlap |
| 3 | `host_alert_count_24h` | Temporal leakage | 4 | Enrichment computed over a centered 24-hour window, so it includes alerts raised in the 12 hours after the flow | Read the enrichment function; check `max(ts of contributing alerts) > flow ts` |
| 4 | `cmdline_window` | Temporal leakage via join | 6 | The 10-minute window is symmetric. It captures IR containment commands (`Stop-Service`, `Disable-LocalUser`, `quarantine`) run after the detection. TF-IDF learns the response, not the attack. | Inspect top TF-IDF tokens per class; they are defender verbs |
| 5 | `source_sensor` | Proxy leakage, invisible to importance ranking | 9 | Sensor-B tapped VLAN 40 only; 94% of positives are sensor-B rows. Moderate importance, so learners who prune "top features" miss it. | Label rate per category; ablation (drop and retrain) shows a larger PR-AUC drop than its importance implies |
| 6 | `dst_port` | Distribution artefact | 5 | Week-1 red team hit 3389 and 445. Not leakage in the strict sense, but week 2 hits 5985 and 22. Model learns "port 3389 means attack". | Debate point; the week-2 gate settles it |
| 7 | `history`, `conn_state` | Not leakage. Genuine signal. | 7, 8 | `S` (SYN only), `S0`, `REJ` are reconnaissance shapes | Learners who drop these lose real signal; the probe penalizes it |

Feature 7 is the misleading feature. It ranks high and is legitimate. A learner who reasons "high importance means suspicious" and drops it has learned the wrong rule.

### 3.4 LabRunner flow

**Step 1: Build the initial feature set and train the quick model**

STATE: joined table with all columns available.

Learner action: select features and encoding. LabRunner trains a RandomForest (fixed seed, 200 trees, class_weight balanced) with 5-fold stratified random CV and reports accuracy, ROC-AUC, PR-AUC.

Design targets for the all-features model: accuracy 0.998, ROC-AUC 0.999, PR-AUC 0.99.

System response: "Your model is ready for the CISO deck. Before you send it, run the label-shuffle test."

**Step 2: Label-shuffle test (graded, mandatory)**

Learner action: shuffle `label`, retrain, report PR-AUC.

PROBE: shuffled PR-AUC should sit at the base rate (about 0.006). If the learner's shuffled model still scores above 0.05, the learner has a fit-before-split leak in encoding (see Step 4) and LabRunner says so.

BRANCH feedback (test passes): "Good. The model is learning something in the labels. Now the question is whether it is learning the attack or learning the labeling process."

**Step 3: Investigate**

Tools exposed in the kernel: RF feature importance, permutation importance on a held fold, per-category label rate for categoricals, single-feature ROC-AUC, one-at-a-time ablation (drop, retrain, report delta), top TF-IDF tokens by class, and the source of the `host_alert_count_24h` enrichment function.

Learner action: for each feature in the pool, choose keep, drop, or transform, with a one-line justification.

Ablation ladder (design targets, PR-AUC after each removal, cumulative):

| Removed | PR-AUC |
| --- | --- |
| nothing | 0.99 |
| `analyst_note`, `ticket_id` | 0.97 |
| `orig_ttl` | 0.94 |
| `host_alert_count_24h` | 0.88 |
| `cmdline_window` (or re-windowed to past-only) | 0.83 |
| `source_sensor` | 0.74 |
| `dst_port` (or bucketed) | 0.71 |

The honest week-1 model lands near 0.71. LabRunner must say plainly that this lower number is the correct outcome.

Decision point feedback samples:

- Learner keeps `orig_ttl`: "Show me a TTL value that distinguishes lateral movement from a file share. You cannot, because TTL distinguishes hosts, not behaviors. The red team's next engagement will run from a Windows box."
- Learner drops `history`: "You dropped the SYN-only flag. Explain what in a SYN-only flow is an artefact of labeling rather than of the traffic. If you cannot, restore it."
- Learner keeps `source_sensor`: "Label rate on sensor-B is 3.1%. On sensor-A it is 0.02%. Your model has learned which cable the red team was plugged into."
- Learner drops `host_alert_count_24h` outright: "Acceptable. Better: recompute it as a trailing window ending at the flow timestamp. Enrichment features are among the most useful in a SOC, when they only look backward."

**Step 4: Choose encodings**

Decision point for `service` (30 values) and `dst_port` (about 4,000 values).

| Choice | Feedback |
| --- | --- |
| One-hot both | `dst_port` explodes to 4,000 columns. Works, slow, and every port seen once becomes a memorized attack indicator. |
| Ordinal | "Port 445 is not less than port 3389. Trees tolerate this; anything with a distance metric does not. You will reuse these features with cosine similarity in Module 3." |
| Target encoding fitted on the full dataset | Label-shuffle test now fails (shuffled PR-AUC 0.30). "You encoded the label into the feature before splitting. This is the most common leak in Kaggle notebooks and in production feature stores." |
| Target encoding inside CV folds | Acceptable, with a warning about the week-2 gate. |
| Bucket `dst_port` into well-known, registered, ephemeral, plus a `is_admin_port` flag for a fixed short list | Recommended. |

**Step 5: The week-2 gate**

Learner submits the final feature set and encoding. LabRunner trains on week 1 and scores on the private week-2 file.

| Learner's model | Week-1 CV PR-AUC | Week-2 PR-AUC (design target) |
| --- | --- | --- |
| All features kept | 0.99 | 0.18 |
| Only label-adjacent removed | 0.97 | 0.24 |
| Honest set | 0.71 | 0.62 |

Then the base-rate step: at the week-2 rate of 1 in 2,000 and the learner's chosen threshold, LabRunner prints TP, FP, PPV, and analyst hours consumed per true positive at 4 minutes per alert. A model at 0.62 PR-AUC with a reasonable threshold produces a PPV in the 5% to 10% band. Learners compute PPV by hand and LabRunner checks it within one percentage point (the syllabus assessment criterion).

### 3.5 Failure modes

- Learner ships the 0.99 model. Week-2 PR-AUC collapses. LabRunner shows the CISO slide with the two numbers side by side.
- Learner target-encodes on full data. Shuffle test fails; LabRunner blocks progression until fixed.
- Learner prunes by importance alone. `source_sensor` survives (rank 9), week-2 score lands at 0.35 with no obvious cause. LabRunner's hint: "Compare ablation delta to importance rank for every remaining feature."
- Learner drops `history` and `conn_state`. Honest model drops to 0.58 on week 2. LabRunner: "You threw out signal. Not every strong feature is a leak."

### 3.6 Instructor notes

- The core lesson is procedural: importance ranking is not a leak detector. Ablation and per-category label rates are. Say this before the lab and again after.
- The `cmdline_window` leak is the one most SOC engineers will recognize from their own environment. Any feature that joins on a symmetric time window around an event will pull in the response to that event.
- Expect argument on `dst_port`. Let it run for two minutes, then show the week-2 numbers.
- Connect forward: the `orig_ttl` lesson reappears in Module 5 as memory records that identify the injector rather than the injection, and in Module 8 as Sigma rules that fire on the red team's hostname rather than the technique.
- Common mistake: learners run the shuffle test once, at the start, and never again after changing encodings. It must run before the gate.

### 3.7 Success criteria

- Label-shuffle PR-AUC below 0.02 on the final feature set.
- Features 1 to 5 removed or transformed to past-only; feature 7 retained.
- Week-2 PR-AUC at or above 0.55. [Design target; the generator determines the ceiling.]
- Written justification per dropped feature that names the leak type (label, temporal, proxy, distribution artefact).
- PPV computed by hand within one percentage point of LabRunner's value.

## 4. Lab 3: Building a Reproducible Pipeline

### 4.1 Scenario

The platform team will run your pipeline every night on the previous day's raw exports. They will not edit anything. They will not tell you if it breaks; they will page you. Package the honest feature set from Lab 2 as a single fitted `sklearn.pipeline.Pipeline`, prove the split is leak-free, serialize it, and prove it runs on a raw file you have never seen.

### 4.2 LabRunner flow

**Step 1: Build the pipeline**

STATE: honest feature set, Lab 1 table.

Learner action: construct a `ColumnTransformer` inside a `Pipeline`.

Required components:

- Numeric: `log1p` on byte and packet counts (heavy-tailed), median imputer for the NaN rate columns from Lab 1, `StandardScaler`.
- Categorical: `OneHotEncoder` for `proto, service, conn_state`; the port bucket transform from Lab 2.
- Derived (via `FunctionTransformer`): packet-rate ratio `orig_pkts / (resp_pkts + 1)`, bytes-per-packet, `zero_duration` flag, and Shannon entropy of `first_payload_hex` (a 64-byte payload prefix column supplied in the flow export).
- Estimator: RandomForest with `random_state` set.

Trap A: fitting outside the pipeline. Many learners call `StandardScaler().fit(X)` on the full table to "look at the numbers" and then reuse it. PROBE compares the fitted scaler's `mean_` against the train-only mean after the split in Step 2. Any mismatch beyond tolerance triggers: "Your scaler has seen the test set. Its mean includes rows the model is supposed to be blind to. This is preprocessing leakage and it is invisible in your metrics."

Trap B: `OneHotEncoder(handle_unknown='error')`. Silent now, fatal in Step 4.

**Step 2: Split the data**

Decision point with three options. LabRunner trains and reports for each.

| Split | Week-1 test PR-AUC (design target) | Feedback |
| --- | --- | --- |
| Stratified random 80/20 | 0.91 | Looks best. This is the trap. |
| Time-ordered, first 80% train, last 20% test | 0.68 | Looks worse. |
| Time-ordered with a 10-minute embargo gap | 0.66 | Looks worst. |

The learner is asked which split to keep and why. Then LabRunner scores each fitted pipeline on the private week-2 file:

| Split | Week-2 PR-AUC (design target) |
| --- | --- |
| Random | 0.41 |
| Time-ordered | 0.60 |
| Time-ordered with gap | 0.61 |

BRANCH feedback (learner chose random): "Your random-split estimate was 0.91. Reality was 0.41. The time-split estimate was 0.68. Reality was 0.60. One of these numbers told you approximately the truth about the future. The other told you a story about the past. Random splits put the 4:07 PM beacon flow in test and the 4:06 PM beacon flow in train, and the model memorized the session. Attacks come in sessions. Sessions straddle random splits."

The embargo gap is explained as the fix for session bleed across the boundary: any session that started in the last ten minutes of train is excluded from test.

**Step 3: Validate leakage guards**

Learner writes assertions. LabRunner checks that each exists and passes:

- `train.ts_utc.max() < test.ts_utc.min()`
- No `uid` or `row_hash` appears in both partitions.
- No `src_ip, dst_ip, dst_port` session (grouped within 10 minutes) appears in both.
- Every fitted transformer's statistics were derived from train only (LabRunner refits on train and compares parameters).
- Label-shuffle test on the pipeline as a whole yields PR-AUC below 0.02.
- `host_alert_count_24h`, if retained, uses only records with `ts < flow.ts`.

BRANCH feedback on missing session check: "Your uid check passed. Your session check does not exist. The 34,000 cross-sensor twins you deduplicated in Lab 1 are gone, but the beacon is still 360 rows of the same session, and 72 of them are in your test set."

**Step 4: Serialize, record the schema, run on the raw file**

Learner action: `joblib.dump` the fitted pipeline; write a `schema.json` containing column names, dtypes, sklearn and pandas versions, the training data `row_hash` Merkle root, the git commit, and the artefact's SHA-256.

LabRunner then runs the pipeline against a raw file it has held back: the week-2 export, unmodified, with the same defects as Lab 1's sources plus one new category (`service = quic`) and one column reordering.

| Failure | Cause | Feedback |
| --- | --- | --- |
| `ValueError: Found unknown categories ['quic']` | `handle_unknown='error'` | "The platform team just got paged at 03:00 because a new protocol appeared. Set `handle_unknown='ignore'` or, better, `infrequent_if_exist`, and log unknowns." |
| Wrong predictions, no error | Learner used positional column indexing; reordering shifted columns | "The pipeline ran. It ran on the wrong columns. Silent failure is the worst failure. Select by name." |
| `KeyError: 'Flow Duration'` | Learner did not put the Lab 1 column-name normalization inside the pipeline | "Your Lab 1 cleaning lives in a notebook cell, not in the artefact. The artefact is what ships." |
| Passes | All defects handled inside the pipeline | Proceed to reproducibility check. |

Reproducibility check: LabRunner loads the artefact twice in fresh processes, runs on the raw file, and compares the SHA-256 of the prediction vector. Mismatch means an unseeded component.

Module 7 preview, delivered as a one-line warning when the learner writes the artefact: "`joblib.dump` produced a pickle. Loading a pickle from anyone you do not trust executes their code. In Module 7 you will weaponize one. For now, record the artefact hash and treat the file as executable."

### 4.3 Failure modes

- Random split chosen and defended. Week-2 gate exposes it.
- Preprocessing fitted on full data. Parameter comparison exposes it.
- Cleaning left outside the pipeline. Raw-file run exposes it.
- Unknown category crash. Raw-file run exposes it.
- Unseeded estimator. Reproducibility check exposes it.

### 4.4 Instructor notes

- The lesson is not "time splits are better". It is "your validation estimate must be built the way the model will be used". Say that sentence; learners will otherwise reduce this to a rule.
- Common mistake: learners add the embargo gap and then evaluate on fewer positives, see a noisier PR curve, and conclude the gap hurt. Show confidence intervals or at least positive counts per partition.
- Emphasize schema recording. In Module 7 the ML-BOM and signing steps build on exactly this file. The `row_hash` Merkle root is the first provenance artefact in the course.
- The week-2 numbers for Lab 3 are lower than the week-2 number for the honest Lab 2 set (0.62) because Lab 3 trains on 80% of week 1 rather than all of it. Preempt the question.

### 4.5 Success criteria

- One `Pipeline` object containing all cleaning, encoding, scaling, derived features, and the estimator.
- Time-ordered split with embargo; all six validation assertions present and passing.
- Artefact plus `schema.json` written; SHA-256 recorded.
- Raw week-2 file processed end to end with no manual edits and no exceptions.
- Two fresh-process runs produce identical prediction hashes.
- Week-2 PR-AUC at or above 0.55. [Design target.]
